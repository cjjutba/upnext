# Event model

The reference for anything touching `src/domain` or `src/db`. Everything here
was read off `src/domain/types.ts` and the `applyEvent` switch in
`src/domain/reducer.ts`.

## Envelope

Every event carries these fields. `append()` in `src/db/eventStore.ts` fills
them; callers never set them.

| Field | Type | Notes |
|---|---|---|
| `id` | ULID | Globally unique and time sortable. The canonical replay order is `id` ascending |
| `sessionId` | UUID | Generated by `startSession` |
| `deviceId` | UUID | One per install, in `localStorage` under `upnext-device-id` |
| `seq` | number | Per device, monotonic. Comes from the `meta` table. Reserved for multi-device ordering, not read during replay |
| `ts` | number | Wall clock ms. Timers derive from this, so a resume replays identically |
| `v` | `1` | Schema version. Nothing reads it yet. Bump only for a breaking payload change |

## The 14 event types

Guards run in order. When any guard fails the reducer returns the state
unchanged. That is not an error path, it is the design: a log written by
another device or a newer build must never crash replay.

| Type | Payload | Guards | Effect |
|---|---|---|---|
| `session-started` | `courts`, `template`, `config.winCap` | not already started | Resets to `emptyState()` with `sessionId`, `startedAt = ts`, `courtCount`, `rule` |
| `rule-changed` | `template`, `config.winCap` | started, not ended | Replaces `rule`, and nothing else. Takes effect on the next fill, including games started under the old mode. Courts already playing keep their lineups; no `game-lineup-changed` is ever emitted by a switch. The board confirms it in `ModeChangeModal` before appending |
| `player-checked-in` | `playerId` | started, not ended, not queued, not playing | Appends to `checkedIn` if new, clears from `departed` and `sittingOut`, pushes to the queue back |
| `player-departed` | `playerId` | must be in the queue | Removes from queue and `sittingOut`, adds to `departed`, resets the win streak. Cannot depart mid-game or twice |
| `player-sat-out` | `playerId` | in queue, not already sitting | Adds to `sittingOut`. The queue position is kept |
| `player-returned` | `playerId` | currently sitting out | Removes from `sittingOut` |
| `game-started` | `court`, `pairs` | started, not ended; court empty, not closed, within `1..courtCount`; four distinct players; all queued and none sitting out | Removes the four from the queue, creates the active game with `startedAt = ts` |
| `game-lineup-changed` | `court`, `pairs` | court has an active game; four distinct; any added player is queued and not sitting out | Swaps the pairs. Replaced players go to the queue front. `startedAt` is untouched, so the timer keeps running |
| `game-finished` | `court`, `winnerPair?`, `score?` | court has an active game; `winnerPair` is `undefined`, `0`, or `1` | Ends the game, bumps `gamesPlayed` for all four, appends to `finishedGames`, then places the four in the queue by mode. See below |
| `court-closed` | `court` | not already closed; within `1..courtCount` | Voids any game in progress without counting it and sends its four to the queue **front**, resets their streaks, adds to `closedCourts` |
| `court-reopened` | `court` | currently closed | Clears the closed flag. The command then refills |
| `court-added` | none | started, not ended | `courtCount + 1`. Courts are only ever added. Closing covers taking one out of service |
| `event-undone` | `targetEventId` | none | No direct effect. `replay()` handles it through `computeSkipped()` |
| `session-ended` | none | started, not ended | `ended = true`, `endedAt = ts` |

`score` is on the `game-finished` payload and no UI writes it yet.

## Queue placement on finish

The subtle part of the whole reducer, and the thing to get right. Queue order
is not bookkeeping, it is the input the template layer reads next: `nextLineup`
infers who kept the court by looking at the front of the queue.

| Situation | Resulting queue |
|---|---|
| Any non-winners mode, or no `winnerPair` | `[...queue, ...allFour]` in lineup order: pair 0 then pair 1. All four streaks reset. `pairingCycle` increments |
| `winners-stay`, under the cap | `[...winners, ...queue, ...losers]`. Winner streaks increment, loser streaks reset |
| `winners-stay`, at the cap | `[...queue, ...losers, ...winners]`. Losers go back first, so they re-enter ahead of the winners. All four reset |
| `winners-split`, both winners under the cap | `[...winners, ...queue, ...losers]` |
| `winners-split`, one winner capped | `[...stayer, ...queue, ...losers, ...cappedWinner]`. Each winner caps individually |

`wins` only increments in the winners modes. Two other placements go to the
**front** rather than the back: players from a court that was just closed, and
a player pulled off court by a lineup change. Both were removed from a game
through no fault of their own.

## SessionState

Every field is derived by replay and none is stored. From
`src/domain/types.ts`.

| Field | Notes |
|---|---|
| `sessionId`, `started`, `ended`, `startedAt`, `endedAt` | Session lifecycle |
| `courtCount` | Grows via `court-added`, never shrinks |
| `rule` | `{ template, winCap }`. Seeded by `session-started`, replaced by `rule-changed` |
| `checkedIn` | Check-in order. Grows only. Departures are tracked separately, not removed here |
| `sittingOut` | Players who keep a queue spot but are skipped when forming games |
| `departed` | Left for the night. A later check-in clears this |
| `queue` | Waiting order, front first. Sitting-out players stay in place |
| `games` | `Record<court, ActiveGame>`. A missing key means an empty court |
| `closedCourts` | Out of service. Never filled |
| `gamesPlayed`, `wins` | Per player counters |
| `consecutiveWins` | Current streak on court, for the win cap. Reset when a player leaves the court |
| `finishedGames` | Full history this session. Feeds pairing history and the summary |
| `pairingCycle` | Incremented on every non-winners finish, read by nothing. Kept for event compatibility. Rotation now comes from `gamesTogether()` |

## Undo and redo

Undo is an event, which is why redo comes free.

`computeSkipped(events)` returns the ids that replay must skip. An event is
skipped when at least one non-skipped `event-undone` targets it. That
definition is recursive: an `event-undone` that targets another `event-undone`
cancels it, which reinstates the original. The lookup memoizes and seeds each
id as `false` before recursing, which keeps a malformed cycle from hanging
replay.

- `undoTarget(events)` scans from newest, skipping `event-undone` events,
  already-skipped events, and `game-started` fills, and returns the first real
  action. Fills are never undone directly: skipping the action that caused one
  invalidates the fill on replay (the court is still occupied, its players
  never queued), so a single undo reverts a team win together with the refill
  it triggered. It returns `null` at `session-started`, which is never
  undoable.
- `redoTarget(events)` scans from newest, skipping skipped events. The first
  `event-undone` it meets is the redo target. Any other event type that is not
  `session-started` returns `null`, so taking a new action clears the redo.

The UI offers sequential undo and redo only. Dangling states cannot occur.

`useSession` runs every log mutation through a single promise queue. Without
it, two fast taps can merge events into memory in an order a reload would not
reproduce, and a double tap on undo can target the same event twice, which
breaks the redo chain. `src/state/useSession.test.tsx` pins both cases.

## Templates and pairing

A template never runs during replay. It runs inside a command, and the lineup
it picks is written into the `game-started` event.

`nextLineup(state, lastFinished, ratings)` in `src/domain/templates.ts`:

1. Eligible players are the queue minus anyone sitting out. Fewer than four
   returns `null`. There is never a game of three.
2. If a winners template just finished a game, queue position tells the
   function who kept the court:
   - `winners-stay` with both winners at the front: `[[a,b],[c,d]]`.
   - `winners-split` with both at the front: `[[a,c],[b,d]]`.
   - `winners-split` with one at the front: `[[a,b],[c,d]]`.
   - Winners who were capped are already at the back, so this falls through.
3. `balanced` and `social` call `pickPairing()`.
4. Everything else calls `freshFill()`.

The four players are always the front four eligible. Only the partition
changes, among `[[a,c],[b,d]]`, `[[a,b],[c,d]]`, and `[[a,d],[b,c]]`.

### Scoring

`pickPairing()` scores all three partitions and takes the lexicographic
minimum, first partition winning a tie.

| Mode | Score tuple |
|---|---|
| `balanced` | `[ratingImbalance, partnerRepeats, opponentRepeats]` |
| `social` | `[partnerRepeats, opponentRepeats, 0]` |

Unrated players count as 3. Repeat counts come from `finishedGames` plus games
in progress, a partnership being two players on the same team and an opponent
meeting being two on opposite teams.

When all three partitions score identically, which is what a closed group of
four unrated players produces, the tie breaks on
`gamesTogether(state, four) % 3`: how many finished games those exact four
have played together. `freshFill()` uses the same rotation for its
exactly-four case.

That counter matters more than it looks. It is stable across an unrelated
court finishing, so the Up next preview always equals the fill it promises.
Using the session-global `pairingCycle` here was a real bug, fixed in `c2db7ef`.

## Dexie schema

Database `upnext`, version 1, in `src/db/db.ts`.

```
players:       'id, name, createdAt'
sessionEvents: 'id, sessionId, type, [type+sessionId], [sessionId+seq]'
meta:          'key'
```

- `[type+sessionId]` is the sessions table. `listSessions()` pulls
  `session-started` and `session-ended` rows through it, so history renders
  without replaying anything and without a third table.
- `[sessionId+seq]` is reserved for multi-device sync ordering. Replay sorts
  by ULID `id` instead.
- `meta` holds one row, `{ key: 'seq', value: n }`, incremented inside the
  same transaction as each append.
- `players.id` is a UUID from `crypto.randomUUID()`, never a Dexie
  autoincrement, which would collide the moment a second device syncs a roster.

## Export and import

`exportSession()` produces:

```json
{ "format": "upnext-session", "v": 1, "events": [...], "players": [...] }
```

The whole roster ships on purpose, so a device handoff doubles as a roster
sync. `importSession()` rejects anything without the right `format`, then:

- Events go through `bulkPut`, a union by id. Importing the same file twice
  changes nothing.
- Players merge by UUID, last write wins on `updatedAt`, with ties going to
  the incoming row.

An imported session with no `session-ended` event is live and resumes like any
other. That is the handoff story and the crash story at once.
